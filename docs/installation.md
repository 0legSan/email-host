# Установка Email Host

Статус: подготовка первого публичного релиза. Установщик и контейнерная поставка проверяются локально. Рабочая публичная команда пока не опубликована. Не запускайте инструкцию старого production-развёртывания как установку на новый сервер.

## Как будет выглядеть начало

После выпуска и проверки первого релиза команда `curl -fsSL https://emailhost.olegsan.tech/install.sh | sudo bash` загрузит мастер с сайта проекта. Пока этот адрес не является поддерживаемым каналом установки.

Скачанный скрипт выполняется с правами администратора сервера. Перед запуском можно скачать его в файл и прочитать. HTTPS и контрольная сумма защищают доставку от случайного повреждения; они не заменяют доверие к издателю скрипта.

Мастер спрашивает:

1. Куда ставить: пустой сервер, существующий Traefik или существующий Nginx.
2. Домены. Например, `mail.example.com`, `convex.mail.example.com`, `convex-site.mail.example.com`. Для двух служебных доменов предлагаются значения по основному.

Затем показывает план установки и просит его подтвердить. На нестандартном существующем proxy могут потребоваться уточнения сети, HTTPS entrypoint или подключения конфигурации.

База, секреты сессий, ключи шифрования и JWT настраиваются автоматически. Начальный вход владельца создаётся как `owner@<основной-домен>`, пароль генерируется. Это идентификатор входа в приложение, ему не нужен существующий почтовый ящик для подтверждения. Доступ сохраняется в закрытом файле сервера; мастер укажет его расположение.

## Что подготовить

- Linux-сервер с поддерживаемой архитектурой опубликованных образов. Проверенные ОС и ресурсы будут перечислены после стендовой проверки. Первичная автоматическая подготовка Docker рассчитана на Debian/Ubuntu с apt.
- DNS-записи выбранных доменов на сервер. Проверьте и A, и AAAA, чтобы IPv6 не указывал на другой сервер.
- Доступ к HTTP/HTTPS для выбранного proxy и исходящий доступ к почтовым провайдерам. Проверьте ограничения SMTP у своего хостинга.
- Для общего инстанса с настоящей почтой других людей определите правила обработки данных, доступ и ответственность владельца.

Convex использует отдельные публичные адреса backend и HTTP actions. PostgreSQL и административные ключи не должны становиться общедоступными.

## Три режима

| Режим | Что делает установка | Что сохраняет владелец существующего сервера |
| --- | --- | --- |
| Пустой сервер | Отдельный Compose project с PostgreSQL, Convex, API, web и Caddy. Caddy получает и продлевает HTTPS-сертификаты. Публично используются 80/443. | Остальные каталоги и приложения не включаются в этот project |
| Traefik | Приложение подключается к существующей Docker-сети proxy. Создаются маршруты только выбранных доменов. | Свой Traefik, его настройки сертификатов и остальные маршруты |
| Nginx на хосте | Сервисы открываются только на loopback. Готовится отдельный конфиг с WebSocket forwarding. | Свои virtual hosts и управление HTTPS. Мастер даёт шаг подключения и не объявляет сайт готовым до успешной проверки |

Для первого выпуска Nginx в произвольном контейнере и Docker Swarm не являются автоматически поддерживаемыми вариантами. Нельзя безопасно угадать любую внешнюю сеть, пути сертификатов и правила чужого proxy по одним доменам.

## Первый запуск и повтор

Компоненты запускаются по порядку: база и Convex, настройка авторизации и публикация функций, затем API/web и публичный вход. Это новая установка; импорт данных владельца другого сервиса в неё не входит.

При ошибке мастер сообщает незавершённый этап. Не удаляйте конфигурацию и не генерируйте новые ключи ради повторного запуска. Утеря `MAIL_CREDENTIAL_SECRET` лишает возможности расшифровать сохранённые реквизиты почтовых провайдеров.

Повторный запуск установки должен сохранять существующие секреты. Установка не является командой обновления, изменения доменов или перехода на другой proxy.

## После входа

Подключите ящик через интерфейс и проверьте чтение и отправку. Используйте пароль приложения, если этого требует почтовый провайдер. Выберите русский или английский в настройках. Настоящие письма и пользовательские названия не переводятся.

PWA, уведомления и фоновые возможности зависят от браузера и HTTPS. Офлайн доступны только ранее сохранённые данные конкретного браузера, а не вся почта на сервере.

## Резервные копии и обновления

Сохраняйте зашифрованные копии конфигурации с ключами и данные PostgreSQL/Convex вне сервера. Одна копия контейнерного образа не является резервной копией почты и настроек.

Перед обновлением нужны backup, проверка совместимости приложения с версией Convex и проверенный порядок восстановления. Не заменяйте теги всех компонентов на `latest`. Установщик первого выпуска не должен автоматически обновлять обнаруженный инстанс.

Практические команды backup, restore и upgrade будут объявлены поддерживаемыми только после проверки восстановления на отдельном инстансе. Не выполняйте `docker compose down -v` для обновления: команда удаляет volumes с данными.

## Для сопровождающего релиз

`bash scripts/build-public-release.sh VERSION` готовит локальные OCI-архивы application images и deployment archive. По умолчанию запрашиваются Linux amd64/arm64. Это сборка, она ничего не публикует в GitHub или GHCR.

`--package-only` собирает только архив deployment-файлов и не означает, что готов полный релиз. Перед публичным выпуском образы должны быть опубликованы под точной версией, архив проверен по своим контрольным суммам, а установка пройдена на отдельном сервере.

Сборка и существование этого документа не подтверждают готовность публичной установки. Перед выпуском нужны проверка состава публикации, лицензий, публичного DNS/TLS и полного пользовательского сценария.
